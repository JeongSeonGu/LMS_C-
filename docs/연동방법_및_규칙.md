# LmsAgent(C#) ↔ WorkSupport 서버 연동방법 및 규칙

> 이 문서는 `README.md`의 기능 설명과 별개로, **"이 C# 프로그램이 서버와 정확히 어떻게
> 통신하는가"만 한 곳에 모은 기술 참고 문서**입니다. 서버 팀이 작성한 원본 규칙 문서
> (`docs/웹소켓_데이터통신규칙.md`, `docs/복무_할일_연동가이드.md`,
> `docs/학사달력외_연동가이드.md`)의 세부 프로토콜을 대체하지 않으며, 그 문서들이
> "무엇을 어떻게 보낼지"의 1차 출처입니다. 이 문서는 "그래서 이 앱의 어느 파일이
> 그걸 실제로 구현하는지"를 빠르게 찾기 위한 지도 역할을 합니다.

---

## 0. 연동되는 것 / 안 되는 것

| 구분 | 서버(DB)·웹 화면과 연동 | 담당 파일 |
|---|---|---|
| 로그인 세션, 학사일정, 복무, 할일, 요청사항, 알림, 법정연수, 실시간(웹소켓) | ✅ 연동됨 | 아래 각 절 참고 |
| SSO 자동 로그인 | ✅ 연동됨(§2) | `WorkSupportApiClient.GetSsoTicketAsync`, `WorkJournalService.OpenLinkWithSsoAsync`, `TrayApplicationContext.OnWorkSupportPageClicked` |
| **개인일정** | ❌ **로컬 전용 — 서버·웹과 절대 연동되지 않음** | `Services/PersonalScheduleStore.cs` |
| **쪽지(스티커 메모)** | ❌ **로컬 전용** | `Services/StickyNoteService.cs` |
| 업데이트(버전 확인·다운로드) | 서버의 `manifest.json`만 조회(학사 데이터 API와는 무관) | `Services/UpdateService.cs` |

개인일정과 쪽지는 이 문서의 "연동" 범위 밖입니다 — 실수로 동기화 로직을 추가하지
않도록, 이 둘을 건드릴 때는 항상 "로컬 파일에만 쓴다"는 전제를 지켜야 합니다.

## 1. 세션 모델 — WSSESSID는 두 개다

WorkSupport 서버는 JWT가 아니라 **PHP 세션 쿠키(`WSSESSID`)** 기반 인증입니다. 이 앱에서
`WSSESSID`가 관여하는 지점은 **서로 독립된 두 곳**입니다.

1. **C# 자신의 세션** — `WorkSupportApiClient`가 내부 `CookieContainer`로 들고 있습니다.
   `php/auth/ws_login.php` 로그인 시 발급되며, 이후 모든 `SchoolCalendar/php/api/*`,
   `php/features/*` 호출에 자동으로 실립니다.
2. **SSO로 연 브라우저의 세션** — `php/auth/sso_login.php?token=...`을 브라우저가 열면
   서버가 **그 브라우저용으로 새 `WSSESSID`를 발급**합니다. C#의 세션과는 다른 값입니다.

**이 둘이 독립적이라는 사실이 실무적으로 의미하는 것**:

- C#에서 로그인한 상태에서 SSO로 웹을 열어 그 브라우저에서 로그아웃해도, 서버가
  **세션 자체를 강제로 끊지는 않습니다** — 각 `WSSESSID`는 자연 만료 전까지 그대로
  유효합니다. 다만 서버가 로그아웃 시 `work.session.revoked` 이벤트를 발행해 주므로
  (§3-1), C#은 그 알림을 받고 **스스로 화면을 로그아웃 상태로 맞출 수 있습니다.**
- 반대로 C#에서 로그아웃하면 같은 이벤트가 발행되지만, 이미 열려 있는 브라우저 탭이
  그 이벤트를 실시간으로 반영하는지는 웹 쪽 구현에 달려 있습니다(이 저장소의 책임 범위 밖).
- `SessionWatcherService`(§3-2)는 이 이벤트를 놓치거나 웹소켓이 끊긴 경우의 폴백이며,
  세션이 실제로 만료된 경우도 함께 잡아냅니다.

## 2. SSO(자동 로그인)

**목적**: C#에서 이미 로그인된 상태로 교무업무 웹을 열 때, 브라우저가 다시 로그인 화면을
보여주지 않게 한다.

```
C#(기존 로그인 세션) ──GET──▶ php/auth/sso_ticket.php ──발급──▶ { token, expiresIn, loginUrl }
                                                                     │
                                                Process.Start(loginUrl [+ &next=...])
                                                                     │
시스템 브라우저 ──GET──▶ php/auth/sso_login.php?token=...&next=... ──302──▶ 대시보드(또는 next)
```

- `WorkSupportApiClient.GetSsoTicketAsync()` — `GET php/auth/sso_ticket.php`를 C#의
  세션 쿠키로 호출. 응답: `{ ok, data: { token, expiresIn, loginUrl } }`. 토큰은
  **40초짜리 1회용**이라 저장하지 않고 받은 즉시 사용한다.
- 티켓 발급은 **그 순간 C#이 실제로 로그인되어 있어야만** 성공한다(로그아웃/세션 만료 시
  401 + `ok:false`).
- **두 가지 호출 지점**:
  1. `TrayApplicationContext.OnWorkSupportPageClicked` — "교무업무 페이지" 메뉴.
     `next` 없이 `loginUrl`만 그대로 연다 → 대시보드로 이동.
  2. `WorkJournalService.OpenLinkWithSsoAsync` — 업무 일지의 요청사항/알림/법정연수
     항목 클릭. **상세 페이지로 바로 이동해야 하므로** `loginUrl`에
     `next=<url-encode(상세 주소의 상대경로)>`를 덧붙여서 연다.
- **`next`는 반드시 이 서비스 안의 상대경로(`/SchoolWork/WorkSupport/...`)여야 한다.**
  서버(`sso_login.php`)가 오픈 리다이렉트 방지를 위해 스킴이 있는 절대 URL은 전부 무시하고
  대시보드로 보낸다(서버 팀 반영 완료, SSO 자동 로그인 적용 안내.md §5-7). 요청사항·알림·
  법정연수 API가 내려주는 `link` 필드는 원래 이 형식의 상대경로라서 그대로 쓰면 된다.
  토큰이 만료·중복사용 등으로 실패해 로그인 화면으로 돌아가는 경우에도, 서버가
  `redirect=<next>`를 함께 붙여줘서 사용자가 수동으로 로그인하면 원래 페이지로 이어서
  이동한다(`index.html`의 기존 `?redirect=` 처리를 그대로 탄다).
- 두 지점 모두 실패 시(로그인 전, 티켓 발급 실패) 예외를 삼키고 원래 주소를 그대로 연다
  — 자동 로그인이 안 되더라도 수동 로그인은 항상 가능해야 한다.

## 3. 세션 감시(로그아웃/만료 동기화)

두 가지 경로로 "다른 곳에서 로그아웃됨"을 반영한다.

### 3-1. 실시간 — `work.session.revoked` (§1의 한계를 해소한 서버 기능)

`ws_logout.php`가 호출될 때(웹이든 C#이든 어느 쪽이든) 서버가 그 계정의 개인 Room
(`user:<id>`)으로 `work.session.revoked` 도메인 이벤트를 발행한다(서버 팀 반영 완료,
웹소켓_데이터통신규칙.md §7-B). `TrayApplicationContext.OnDomainEventReceived`가 이
타입을 받으면 즉시 `SessionManager.Clear()`를 호출하고 트레이 풍선 알림을 띄운다.

- 별도 모듈 구독이 필요 없다 — 로그인 시 자동으로 들어가는 개인 Room을 통해 온다.
- `WebSocketClientService.ShouldHandle`의 §7 공통 처리(중복 제거·에코 억제·리비전 비교)를
  그대로 통과한다 — scope `"session"`이 처음 등장해도 코드 수정 없이 정상 동작한다
  (내부 `_revisions` 딕셔너리는 scope별로 독립적이라 새 scope는 자동으로 초기 통과된다).
- 이 이벤트는 **강제 로그아웃이 아니라 알림**이다 — 서버가 다른 세션을 직접 끊지 않으며,
  그 세션은 자연 만료 전까지 서버 쪽에서는 계속 유효하다. 받은 쪽이 스스로 화면만 로그아웃
  상태로 맞춘다.
- 이 앱은 자체 "로그아웃" 버튼이 없어(로그인만 있음) 원본 안내의 "내가 방금 로그아웃 버튼을
  눌러서 온 이벤트면 무시" 로직은 적용하지 않았다 — 받는 즉시 처리해도 중복될 일이 없다.

### 3-2. 폴백 — 3분 주기 세션 확인

`Services/SessionWatcherService.cs`가 로그인 중일 때 **3분마다** `ws_me.php?peek=1`을
불러 C#의 세션이 여전히 유효한지 확인한다. 웹소켓 연결이 끊겼거나 위 이벤트를 놓친
경우에도, 세션 자체가 만료됐다면 이 폴백으로 최대 3분 안에는 반영된다.

- 유효하지 않으면(`ok:false`) → `SessionManager.Clear()` 호출 → 로그인 화면·업무 일지가
  즉시 로그아웃 상태로 바뀐다(`SessionChanged` 이벤트 전파).
- 네트워크 오류(조회 자체 실패)는 "세션이 끊겼다"와 구분할 수 없으므로 **로그아웃 처리하지
  않는다** — 일시적 장애로 로그인 상태가 풀리는 것을 방지.

## 4. 실시간 연동(웹소켓)

전체 프로토콜은 `docs/웹소켓_데이터통신규칙.md`가 원본이다. 여기서는 이 앱이 실제로
구독/처리하는 부분만 요약한다.

- 접속 주소: 로그인 후 발급받는 티켓(`Models/Realtime/DeviceTicket`)의 `agentUrl`
  (raw WebSocket, Socket.IO 아님).
- 구독 모듈(`WebSocketClientService.Modules`): `calendar`, `notice`, `request`, `training`.
- 수신 처리 규칙(§7 공통): `eventId` 중복 제거 → `origin.clientId == 내 clientId`면
  버림(에코 억제) → `revision <= 저장된 값`이면 버림 → scope별 처리.
- scope별로 실제 갱신되는 화면(`TrayApplicationContext.OnRealtimeScopeChanged`):

  | scope | 갱신 대상 |
  |---|---|
  | `calendar` (type이 `work.calendar.duty*`) | 복무 배너(`DutyNotificationService.RefreshNow`) |
  | `calendar` (그 외 — 일정/할일/재동기화) | 배경화면 학사달력(`ScheduleOverlayService.RefreshNow`) + 업무 일지 |
  | `request` · `training` · `notice` | 업무 일지만(`WorkJournalService.RefreshNow`) |

- 저장(POST) 요청에는 `X-WS-Client-Type: windows`, `X-WS-Client-Id: <소켓 접속 시 받은 clientId>`
  헤더를 실어 보낸다(`WorkSupportApiClient.AddClientHeaders`) — 서버가 "내가 만든 변경"임을
  알고 나에게는 에코를 보내지 않는다.
- §7-A(담당업무 변경 감지)는 `MyDutyChangeService`가 `DomainEventData.Hint`
  (`DeptFrom`/`DeptTo`)를 보고 판정해 트레이 풍선 알림만 띄운다(화면 갱신 자체는 위 표의
  `calendar` 처리가 이미 담당).

## 5. HTTP API 엔드포인트 — 세 가지 서로 다른 규칙

| API 계열 | 예시 경로 | 본문 형식 | 오류 메시지 키 | 인증 |
|---|---|---|---|---|
| 학사 달력 | `SchoolCalendar/php/api/*` | JSON | `msg` | 조회는 무인증 |
| 인증 | `php/auth/*` | 폼(GET은 쿼리) | `message` | `ws_login`/`sso_ticket` 등은 그 자체가 인증 절차 |
| 부가 기능 | `php/features/*` (요청사항·알림·법정연수·학교정보·공통계정 등) | 폼(`application/x-www-form-urlencoded`, 첨부 시 multipart) | `message` | 조회도 로그인 필수 |

**"학사 달력 API인데 JSON이 아니라 폼으로 보냈다" 또는 그 반대**가 이 코드베이스에서
가장 흔한 실수 지점이다 — 새 엔드포인트를 추가할 때는 반드시 위 표에서 그 경로가 어느
계열인지 먼저 확인할 것.

`WorkSupportApiClient.cs`에 있는 주요 메서드:

| 기능 | 메서드 | 계열 |
|---|---|---|
| 로그인/로그아웃/내 정보 | `LoginAsync`/`LogoutAsync`/`GetMeAsync`/`GetProfileAsync` | 인증 |
| SSO 티켓 발급 | `GetSsoTicketAsync` | 인증 |
| 실시간 접속 티켓 | `IssueDeviceTicketAsync` | 인증 |
| 담당업무/교사 | `GetDepartmentsAsync`/`GetTeacherAsync` | 학사 달력 |
| 학사 일정 CRUD | `GetEventsAsync`/`GetEventAsync`/`AddEventAsync`/`UpdateEventAsync`/`DeleteEventAsync` | 학사 달력 |
| 할일 CRUD | `GetTodosAsync`/`AddTodoAsync`/`UpdateTodoAsync`/`ToggleTodoAsync`/`DeleteTodoAsync` | 학사 달력 |
| 복무 CRUD | `GetDutyStatusAsync`/`AddDutyAsync`/`UpdateDutyAsync`/`DeleteDutyAsync` | 학사 달력 |
| 학교기본정보/공통계정/요청사항/협의사항/길라잡이 | `GetSchoolInfoAsync` 등 | 부가 기능 |
| 요청사항·알림·법정연수 "진행 중" 요약(업무 일지용) | `GetActiveRequestsAsync`/`GetUnreadNoticesAsync`/`GetActiveTrainingAsync` | 부가 기능 |

각 계열의 정확한 필드·이벤트 타입·처리 규칙은 `docs/복무_할일_연동가이드.md`와
`docs/학사달력외_연동가이드.md`를 참고할 것 — 이 문서는 "어느 파일이 그걸 부르는지"만
정리한다.

## 6. 업데이트(버전 확인) — 학사 데이터 연동과는 무관

`UpdateService`가 조회하는 `manifest.json`은 위 학사/복무 API와 완전히 별개의, 순수
버전 배포용 정적 파일이다(`환경설정 > 네트워크 > 업데이트 서버`). 인증도 세션도 쓰지
않는다. 자세한 형식과 배포 절차는 `README.md`의 "업데이트 배포 방법"을 참고.
