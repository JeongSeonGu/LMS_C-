# WorkSupport ↔ Windows ClassLMS 실시간 통신 규칙

> **이 문서의 독자** — Windows ClassLMS(C#) 프로젝트에서 실시간 연동을 구현할 개발자 또는 AI.
> 서버 쪽은 이미 구축·동작 중이며, **서버는 수정하지 않는다**는 전제로 작성했습니다.
> 클라이언트가 지켜야 할 규약만 담았습니다.

| 항목 | 값 |
|---|---|
| 문서 버전 | 1.0 (2026-09-20) |
| 실시간 서버 | `node2.future-class.kr` (Express + Node.js) |
| 웹 서버 | `future-class.kr` (Apache + PHP 8) |
| 접속 방식 | **raw WebSocket** (Socket.IO 아님) |
| 접속 경로 | `wss://node2.future-class.kr/ws-lms` |
| 메시지 형식 | UTF-8 JSON 텍스트 프레임 |

---

## 0. 먼저 읽을 것 — 세 가지 금지 사항

### ① `wss://node2.future-class.kr/ws` 에 붙지 마십시오

같은 서버에 `/ws` 라는 raw WebSocket 엔드포인트가 이미 있지만, **WorkSupport 와 무관한 다른 C# 프로그램 전용**입니다.
고정 공유키로 인증하고 접속자 전원에게 무차별 브로드캐스트하므로, 여기 붙으면
관계없는 메시지를 받게 되고 권한 구분도 되지 않습니다.
**반드시 `/ws-lms` 를 쓰십시오.**

### ② Socket.IO 클라이언트를 쓰지 마십시오

웹 브라우저는 Socket.IO(`/ws-work`)로 붙지만, Windows 쪽은 **표준 WebSocket**(`System.Net.WebSockets.ClientWebSocket`)으로 붙습니다.
SocketIOClient 패키지가 필요 없습니다.

### ③ 소켓으로 받은 내용을 화면에 직접 그리지 마십시오

소켓은 **"무엇이 바뀌었다"는 사실만** 전달합니다. 데이터 본문이 들어있지 않습니다.
알림을 받으면 **기존 HTTP API 를 다시 호출**해서 최신 데이터를 가져와 화면을 갱신합니다.
이 원칙이 무너지면 DB와 화면이 어긋납니다.

## 1. 전체 흐름

```
 [1] 기기 등록 (최초 1회, 관리자가 DB에 등록)
        device_id + 토큰 평문 발급 → 토큰은 DPAPI 로 보관

 [2] 티켓 발급 (접속할 때마다)
        POST https://future-class.kr/.../rt_ticket.php?mode=device
             { device_id, token }
        →    { token(60초), agentUrl, revisions, ... }

 [3] WebSocket 접속
        wss://node2.future-class.kr/ws-lms
        헤더 x-auth-token: <[2]의 token>

 [4] 구독
        send { "type":"subscribe", "modules":["calendar","notice"] }

 [5] 수신 → 재조회 → 화면 갱신
        recv { "type":"domain.event", "data":{ scope, revision, ... } }
        revision 이 내가 가진 값보다 크면
        → 기존 HTTP API 재조회 → UI 갱신 (UI 스레드로 마샬링)
```

## 2. 기기 등록 (최초 1회 · 서버 관리자 작업)

기기마다 긴 임의 토큰을 만들고 **해시만** DB에 넣습니다. 평문은 저장하지 않습니다.

```bash
# 토큰 평문 생성 — 이 값을 C# 프로그램에 넣습니다
openssl rand -hex 24

# bcrypt 해시 생성
php -r "echo password_hash('위에서_만든_토큰평문', PASSWORD_BCRYPT), PHP_EOL;"
```

```sql
INSERT INTO schoolwork_realtime_devices
  (device_id, device_name, user_id, token_hash, client_type, is_active, created_at)
VALUES
  ('pc-teacher-401', '4학년 1반 교무용 PC', 12, '$2y$10$…', 'windows', 1, NOW());
```

| 컬럼 | 설명 |
|---|---|
| `device_id` | 설치 단위 식별자. C# 이 티켓 요청 시 보냄 |
| `user_id` | 이 기기가 대표하는 `school_users.id`. **이 계정의 역할·메뉴권한을 그대로 따릅니다** |
| `token_hash` | bcrypt 해시 (평문 금지) |
| `is_active` | 0 으로 바꾸면 즉시 차단 |
| `last_seen_at` | 서버가 접속 시 자동 갱신 |

> 담임 PC 라면 해당 교사 계정을, 교무용 공용 PC 라면 그에 맞는 계정을 지정합니다.
> 기기를 분실하면 `is_active = 0` 으로 즉시 막을 수 있습니다.

## 3. 티켓 발급

소켓 인증은 **수명 60초짜리 1회용 티켓**으로만 합니다. 기기 토큰을 소켓에 직접 보내지 않습니다.

### 요청

```
POST https://future-class.kr/SchoolWork/WorkSupport/php/auth/rt_ticket.php?mode=device
Content-Type: application/json

{ "device_id": "pc-teacher-401", "token": "<토큰 평문>" }
```

### 응답

```json
{
  "ok": true,
  "data": {
    "token":     "eyJhbGciOi...",
    "expiresIn": 60,
    "agentUrl":  "wss://node2.future-class.kr/ws-lms",
    "agentPath": "/ws-lms",
    "clientId":  "d-3f9a1c2b4e5d6a7b",
    "userId":    12,
    "revisions": { "calendar": 418, "notice": 77, "timetable": 12, ... },

    "url":       "https://node2.future-class.kr",
    "path":      "/ws-work",
    "namespace": "/work"
  }
}
```

| 필드 | 용도 |
|---|---|
| `token` | WebSocket 접속 헤더에 넣을 값. **60초 뒤 만료** |
| `agentUrl` | 접속할 주소. 이것만 쓰면 됩니다 |
| `clientId` | 이 기기의 식별자. 에코 억제에 쓰임 (§7 참고) |
| `revisions` | **접속 시점의 스코프별 리비전.** 로컬 초기값으로 저장 |
| `url`·`path`·`namespace` | **웹 브라우저(Socket.IO) 전용. 무시하십시오** |

### 실패 응답

```json
{ "ok": false, "data": null, "message": "기기 인증에 실패했습니다." }
```

HTTP 401 이면 `device_id` 또는 토큰이 틀렸거나 `is_active = 0` 입니다.

> **티켓은 저장하지 마십시오.** 재접속할 때마다 새로 받습니다.
> 같은 티켓으로 두 번 접속하면 서버가 `replayed` 로 거절합니다.

## 4. WebSocket 접속

```
wss://node2.future-class.kr/ws-lms

요청 헤더
  x-auth-token: <3장에서 받은 token>
```

| 결과 | 의미 |
|---|---|
| `101 Switching Protocols` | 성공 |
| `401 Unauthorized` | 티켓 검증 실패 (만료·서명오류·재사용 등) |

C# 예:

```csharp
var ws = new ClientWebSocket();
ws.Options.SetRequestHeader("x-auth-token", ticket.Token);
await ws.ConnectAsync(new Uri(ticket.AgentUrl), cancellationToken);
```

**연결은 프로그램 전체에서 하나만** 유지합니다(싱글턴). 폼마다 만들지 않습니다.

## 5. 메시지 규격

모든 메시지는 **UTF-8 JSON 텍스트 프레임** 1개입니다. 최상위에 항상 `type` 이 있습니다.

### 5-1. 서버 → 클라이언트

#### `rt.ready` — 접속 직후 1회

```json
{
  "type": "rt.ready",
  "data": {
    "userId": 12,
    "schoolId": "jsg",
    "role": "teacher",
    "serverTime": "2026-09-20T02:41:50.000Z"
  }
}
```

이걸 받으면 접속이 완료된 것입니다. 이 다음에 `subscribe` 를 보냅니다.

#### `subscribed` / `unsubscribed` — 구독 요청에 대한 응답

```json
{ "type": "subscribed", "data": { "modules": ["calendar","notice"], "denied": [] } }
```

`denied` 에 들어간 기능은 **권한이 없거나 이름이 틀린 것**입니다. 로그에 남기십시오.

#### `domain.event` — 변경 알림 (핵심)

```json
{
  "type": "domain.event",
  "data": {
    "v": 1,
    "eventId": "9f1c8e2a-...",
    "type": "work.calendar.event.updated",
    "scope": "calendar",
    "revision": 419,
    "occurredAt": "2026-09-20T02:41:50.120Z",
    "schoolId": "jsg",
    "op": "updated",
    "resource": { "type": "school_events", "id": "387", "rowVersion": 18 },
    "actor": { "userId": 1024, "name": "정선구" },
    "origin": { "clientType": "web", "clientId": "b-3f9a2c11" },
    "fields": ["deptId"],
    "hint": { "deptFrom": 3, "deptTo": 7 }
  }
}
```

| 필드 | 필수 | 설명 |
|---|:--:|---|
| `v` | ✅ | 스키마 버전. 현재 `1`. 모르는 값이면 무시 |
| `eventId` | ✅ | UUID. **중복 수신 방어에 사용** |
| `type` | ✅ | `[영역].[기능].[대상].[행위]` (§6) |
| `scope` | ✅ | 리비전 비교 단위 (§7) |
| `revision` | ✅ | 이 스코프의 새 리비전 번호 |
| `op` | ✅ | `created` / `updated` / `deleted` |
| `resource` | – | 바뀐 행. `id` 는 **문자열**로 옵니다 |
| `actor` | – | 변경한 사람. 토스트 문구에 쓸 수 있음 |
| `origin` | – | 변경을 일으킨 클라이언트 (§7 에코 억제) |
| `fields` | – | 바뀐 필드명 (있을 때만). 업무가 바뀌면 `"deptId"` 가 들어 있음 |
| `hint` | – | "나와 관련 있는가" 판단용 최소 값. 학사 일정은 `deptFrom` · `deptTo` (§7-A) |

> **payload 에 업무 데이터·개인정보는 들어오지 않습니다.** 최대 8KB 로 제한됩니다.
> 학생 이름, 일정 제목, 본문 같은 것은 절대 오지 않으니 반드시 재조회하십시오.
> `hint` 도 예외가 아닙니다. 담당업무 **번호**처럼 판단에 필요한 숫자만 옵니다.

#### `pong`

```json
{ "type": "pong", "data": { "t": 1789000000000 } }
```

### 5-2. 클라이언트 → 서버

**보낼 수 있는 메시지는 아래 3개뿐입니다.** 그 외는 서버가 조용히 버립니다.

```json
{ "type": "subscribe",   "modules": ["calendar", "notice"] }
{ "type": "unsubscribe", "modules": ["notice"] }
{ "type": "ping" }
```

- 이 채널은 **서버 → 클라이언트 알림 전용**입니다. 데이터 저장·수정은 **HTTP API** 로 하십시오.
- `subscribe` 는 분당 20회로 제한됩니다. 접속 후 한 번만 보내면 됩니다.

## 7. 핵심 알고리즘 — 리비전 처리

이 장이 이 문서에서 가장 중요합니다. **이대로 구현하지 않으면 데이터가 어긋납니다.**

### 왜 필요한가

네트워크는 순서를 보장하지 않고, 재접속 중에 이벤트를 놓칠 수 있습니다.
그래서 "무엇이 바뀌었나"가 아니라 **"내가 가진 것이 최신인가"** 를 기준으로 판단합니다.

`scope` 마다 정수 `revision` 이 있고, 서버에서 변경이 일어날 때마다 1씩 증가합니다.

### 처리 순서

```
domain.event 수신
  │
  ├─ 1. eventId 가 최근 200건 안에 있는가?  → 있으면 버림 (중복 수신)
  │
  ├─ 2. origin.clientId == 내 clientId ?    → 같으면 버림 (내가 만든 변경의 메아리)
  │
  ├─ 3. revision <= 내가 가진 revision[scope] ? → 그러면 버림 (오래된 이벤트)
  │
  ├─ 4. revision[scope] = revision           (먼저 갱신)
  │
  └─ 5. type 을 보고 필요한 HTTP API 만 재조회 → UI 갱신
```

> **4번을 5번보다 먼저** 하십시오. 재조회 중에 다음 이벤트가 와도 중복 조회하지 않습니다.

### 의사 코드

```csharp
private readonly Dictionary<string,int> _rev = new();      // scope -> revision
private readonly Queue<string> _seen = new();              // 최근 eventId
private readonly HashSet<string> _seenSet = new();

bool ShouldHandle(EventPayload ev)
{
    if (string.IsNullOrEmpty(ev.EventId)) return true;

    if (_seenSet.Contains(ev.EventId)) return false;        // 1. 중복
    _seen.Enqueue(ev.EventId); _seenSet.Add(ev.EventId);
    while (_seen.Count > 200) _seenSet.Remove(_seen.Dequeue());

    if (ev.Origin?.ClientId == _myClientId) {               // 2. 내 메아리
        if (ev.Scope != null) _rev[ev.Scope] = ev.Revision;
        return false;
    }

    if (_rev.TryGetValue(ev.Scope, out var cur)
        && ev.Revision <= cur) return false;                // 3. 오래된 이벤트

    _rev[ev.Scope] = ev.Revision;                           // 4. 먼저 갱신
    return true;                                            // 5. 호출부에서 재조회
}
```

### 초기값

티켓 응답의 `revisions` 를 그대로 `_rev` 에 넣습니다. **0 으로 시작하면 접속 직후 불필요한 전체 재조회가 일어납니다.**

### 재동기화

재접속에 성공하면 **반드시** 티켓을 새로 받고, 거기 담긴 `revisions` 와 로컬 값을 비교하십시오.
로컬보다 큰 스코프가 있으면 그 스코프를 재조회합니다. 끊겨 있는 동안 놓친 변경이 이렇게 복구됩니다.

```
재접속 성공
  → 새 티켓의 revisions 와 로컬 _rev 비교
  → 서버 값이 크면 그 scope 재조회 후 _rev 갱신
```

## 7-A. 담당업무(업무) 변경 감지 — "내 업무인가"

웹의 학사 달력에서 일정의 **업무**(담당업무 · 부서)를 바꾸면, 그 일정이
**누구의 일이 되었는지 / 누구의 일에서 빠졌는지** 가 바뀝니다.
로그인한 교사의 업무와 관련된 변경이면 C# 은 알림·목록 반영 같은 처리를 해야 합니다.

### 무엇이 오는가

학사 일정 이벤트(`work.calendar.event.*`)에는 항상 `hint` 가 붙습니다.

| `hint` 키 | 값 | 뜻 |
|---|---|---|
| `deptFrom` | 정수 · `null` | 변경 **전** 업무 id. 새로 만든 일정이면 `null` |
| `deptTo` | 정수 · `null` | 변경 **후** 업무 id. 삭제된 일정이면 `null` · 업무 미지정이어도 `null` |

업무가 실제로 바뀐 경우에는 `fields` 에 `"deptId"` 가 들어 있습니다.
(`deptFrom` 과 `deptTo` 를 직접 비교해도 같은 결과입니다)

> **왜 `hint` 가 필요한가** — 삭제되었거나 내 업무에서 **빠진** 일정은, 다시 조회해도
> "예전에 내 업무였다" 는 사실을 알 수 없습니다. 조회 API 는 **현재** 상태만 주기 때문입니다.
> 그래서 변경 **전** 값(`deptFrom`)을 이벤트에 실어 보냅니다.

### 내 업무 목록 얻기

```http
GET https://future-class.kr/SchoolWork/WorkSupport/php/auth/ws_me.php?peek=1
```

```json
{ "ok": true, "data": {
    "user": { "user_id": 12, "teacher_id": 7, "dept_id": 3, ... },
    "expires_in": 13820,
    "dept_ids": [3, 9]
} }
```

- **`dept_ids` 를 쓰십시오.** `user.dept_id` 는 대표 업무 **1개**뿐입니다.
  한 교사가 여러 업무를 맡는 경우가 흔합니다(N:M).
- 로그인 직후 1회, 이후 **세션 확인(5분 주기) 때마다 함께 갱신**하십시오.
  관리자가 업무 배정을 바꿀 수 있고, 서버는 매번 DB 에서 새로 읽어 줍니다.
- 이 요청은 로그인 세션(`WSSESSID`)이 필요합니다. `복무와할일연동_가이드.md` §2.

### 판정 규칙

```
mine(x)  =  x != null  &&  myDeptIds.Contains(x)

from = hint.deptFrom      to = hint.deptTo
```

| op | 조건 | 판정 | C# 이 할 일 (권장) |
|---|---|---|---|
| `created` | `mine(to)` | **내 업무 새 일정** | 알림 + 목록 추가 |
| `updated` | `!mine(from) && mine(to)` | **내 업무로 배정됨** | 알림 "내 업무로 배정" + 목록 추가 |
| `updated` | `mine(from) && !mine(to)` | **내 업무에서 해제됨** | 알림 "업무 해제" + 목록에서 제거 |
| `updated` | `mine(from) && mine(to)` | 내 업무 일정 **수정**(업무 간 이동 포함) | 조용히 갱신 (필요 시 알림) |
| `deleted` | `mine(from)` | **내 업무 일정 삭제** | 알림 + 목록에서 제거 |
| 그 외 | — | 나와 무관 | 화면 재조회만 (§8) |

**"알림을 띄울지"는 C# 의 몫입니다.** 서버는 사실만 알립니다.
다만 아래 두 가지는 지키십시오.

1. **내가 바꾼 것은 알리지 마십시오.** `origin.clientId == 내 clientId` 이면 이미 서버가 걸러 주지만,
   웹에서 **같은 사용자가** 바꾼 경우(`actor.userId == 내 user_id`)는 오므로,
   그때는 알림 없이 목록만 갱신하는 편이 자연스럽습니다.
2. **같은 `eventId` 로 두 번 처리하지 마십시오.** (§7 중복 방어와 같은 원리)

### 내용(제목·날짜)은 재조회로

`hint` 에는 제목이 없습니다. 알림 문구를 만들려면 다시 읽으십시오.

| 판정 | 조회 방법 |
|---|---|
| 새 일정 · 배정됨 · 수정 | `GET {BASE}/SchoolCalendar/php/api/events.php?action=get&id={resource.id}` |
| 해제됨 · 삭제 | **조회 불가**(삭제된 일정은 `이벤트 없음`). **로컬 캐시의 제목**을 쓰고, 없으면 "내 업무 일정이 삭제되었습니다" 같은 일반 문구 |

→ 그래서 C# 은 **내 업무 일정의 id → 제목·날짜** 를 작게라도 캐시해 두는 편이 좋습니다.

### `hint` 가 없는 이벤트

예전 서버에서 쌓인 이벤트이거나, 다른 경로로 발행된 이벤트일 수 있습니다.
그때는 **재조회 결과와 로컬 캐시를 비교**하는 방식으로 떨어지십시오.

```
캐시에 있던 일정의 deptId ≠ 새로 받은 deptId  → 위 표와 같은 판정
캐시에 없고 새로 받은 deptId 가 내 업무       → 배정됨(또는 새 일정)
재조회가 '이벤트 없음'이고 캐시상 내 업무      → 삭제
```

### C# 의사 코드

```csharp
void OnCalendarEvent(DomainEvent e)
{
    if (!e.Type.StartsWith("work.calendar.event.")) return;
    if (!_seen.Add(e.EventId)) return;                         // 중복 방어

    int? from = e.Hint?.DeptFrom;
    int? to   = e.Hint?.DeptTo;
    bool mine(int? x) => x.HasValue && _myDeptIds.Contains(x.Value);
    bool byMe = e.Actor?.UserId == _me.UserId;                  // 웹에서 본인이 바꿈

    string? kind = e.Op switch
    {
        "created" when mine(to)                => "created",
        "updated" when !mine(from) && mine(to) => "assigned",
        "updated" when mine(from) && !mine(to) => "unassigned",
        "updated" when mine(from) &&  mine(to) => "changed",
        "deleted" when mine(from)              => "deleted",
        _ => null,
    };

    if (kind != null) _ = HandleMyDutyChangeAsync(kind, e.Resource.Id, notify: !byMe && kind != "changed");
    ScheduleRefetch(e);                                         // 화면 재조회는 항상 (§8)
}

async Task HandleMyDutyChangeAsync(string kind, string id, bool notify)
{
    string title;
    if (kind is "unassigned" or "deleted")
    {
        title = _myEventCache.TryGetValue(id, out var c) ? c.Title : "(제목 확인 불가)";
        _myEventCache.Remove(id);
    }
    else
    {
        var ev = await _api.GetEventAsync(id);                  // events.php?action=get
        if (ev == null) return;                                 // 그 사이 삭제됨
        _myEventCache[id] = ev;
        title = ev.Title;
    }

    if (notify) ShowToast(kind switch
    {
        "created"    => $"내 업무에 새 일정: {title}",
        "assigned"   => $"내 업무로 배정되었습니다: {title}",
        "unassigned" => $"내 업무에서 해제되었습니다: {title}",
        "deleted"    => $"내 업무 일정이 삭제되었습니다: {title}",
        _            => $"내 업무 일정이 수정되었습니다: {title}",
    });
}
```

> C# 쪽은 **쿠키를 유지할 수 있는 `HttpClientHandler` + `CookieContainer`** 구조로 만들어 두십시오.
> 나중에 인증이 추가되면 아래 로그인만 덧붙이면 됩니다.
>
> ```

> Content-Type: application/x-www-form-urlencoded
> login_id=<아이디>&login_pw=<비밀번호>
> ```

> **저장(추가·수정·삭제)은 이 문서의 범위가 아닙니다.**
> 할일·복무를 C# 에서 **기록**하려면 `복무와할일연동_가이드.md` 를 보십시오.

## 9. 연결 유지와 재접속

| 항목 | 값 |
|---|---|
| 서버 → 클라이언트 ping | **30초 간격** (WebSocket 프로토콜 ping) |
| pong 미응답 시 | 서버가 연결을 끊음 |
| 티켓 수명 | 60초 (접속 후에는 무관) |

`ClientWebSocket` 은 프로토콜 ping 에 **자동으로 pong 을 보냅니다.** 별도 처리가 필요 없습니다.
응용 수준 확인이 필요하면 `{"type":"ping"}` 을 보내 `pong` 을 받으십시오.

### 재접속 정책

```
연결 끊김 감지
  → 1초 대기 후 재시도
  → 실패하면 2초, 4초, 8초… 최대 30초까지 늘림 (지수 백오프)
  → 매 시도마다 티켓을 새로 발급받을 것
  → 성공하면 subscribe 다시 보내고 재동기화 (§7)
```

**즉시·무한 재시도를 하지 마십시오.** 서버 로그가 도배되고 부하가 걸립니다.

### 인증 실패가 반복될 때

`401` 이 **5회 연속** 나오면 설정 문제입니다. 재시도를 멈추고 사용자에게 알리십시오.

| 원인 | 확인할 것 |
|---|---|
| 기기 토큰이 틀림 | DPAPI 로 저장한 값이 깨지지 않았는지 |
| `is_active = 0` | 관리자가 기기를 차단함 |
| 시계 차이 | PC 시간이 서버와 1분 이상 차이나면 티켓이 만료로 판정됨 |

## 11. C# 구현 골격

```csharp
public sealed class RealtimeClientService
{
    private static readonly Lazy<RealtimeClientService> _inst =
        new(() => new RealtimeClientService());
    public static RealtimeClientService Instance => _inst.Value;

    private ClientWebSocket? _ws;
    private string? _myClientId;
    private readonly Dictionary<string,int> _rev = new();
    private readonly string[] _modules = { "calendar", "notice" };

    /// <summary>스코프가 바뀌었을 때 발생. UI 스레드로 마샬링해서 사용할 것.</summary>
    public event Action<string, string>? ScopeChanged;   // (scope, type)

    public async Task StartAsync(CancellationToken ct)
    {
        var delay = TimeSpan.FromSeconds(1);

        while (!ct.IsCancellationRequested)
        {
            try
            {
                var ticket = await IssueTicketAsync(ct);       // §3
                MergeRevisions(ticket.Revisions);              // §7 재동기화

                _myClientId = ticket.ClientId;
                _ws = new ClientWebSocket();
                _ws.Options.SetRequestHeader("x-auth-token", ticket.Token);
                await _ws.ConnectAsync(new Uri(ticket.AgentUrl), ct);

                await SendAsync(new { type = "subscribe", modules = _modules }, ct);

                delay = TimeSpan.FromSeconds(1);               // 성공했으니 백오프 초기화
                await ReceiveLoopAsync(ct);                    // 끊길 때까지
            }
            catch (Exception ex)
            {
                Log.Warn($"[Realtime] {ex.Message}");
            }

            await Task.Delay(delay, ct);
            delay = TimeSpan.FromSeconds(Math.Min(delay.TotalSeconds * 2, 30));
        }
    }

    private async Task ReceiveLoopAsync(CancellationToken ct)
    {
        var buf = new byte[16 * 1024];
        var sb  = new StringBuilder();

        while (_ws!.State == WebSocketState.Open && !ct.IsCancellationRequested)
        {
            var r = await _ws.ReceiveAsync(new ArraySegment<byte>(buf), ct);
            if (r.MessageType == WebSocketMessageType.Close) break;

            sb.Append(Encoding.UTF8.GetString(buf, 0, r.Count));
            if (!r.EndOfMessage) continue;                     // 조각난 프레임 이어붙이기

            var json = sb.ToString(); sb.Clear();
            HandleMessage(json);
        }
    }

    private void HandleMessage(string json)
    {
        var msg = JsonSerializer.Deserialize<ServerMessage>(json);
        switch (msg?.Type)
        {
            case "rt.ready":
                Log.Info("[Realtime] 접속 완료");
                break;

            case "subscribed":
                if (msg.Data?.Denied?.Length > 0)
                    Log.Warn("[Realtime] 구독 거절: " + string.Join(",", msg.Data.Denied));
                break;

            case "domain.event":
                var ev = msg.Data!.ToEventPayload();
                if (!ShouldHandle(ev)) return;                 // §7
                ScopeChanged?.Invoke(ev.Scope, ev.Type);
                break;
        }
    }
}
```

## 12. 반드시 지킬 것 (체크리스트)

- [ ] `/ws-lms` 에만 접속했는가 (`/ws` 아님)
- [ ] 연결은 프로그램 전체에 **하나**인가
- [ ] 티켓을 저장하지 않고 접속할 때마다 새로 받는가
- [ ] `eventId` 중복 검사를 하는가
- [ ] `origin.clientId` 로 내 메아리를 거르는가
- [ ] 내 업무 판정에 `ws_me.php` 의 **`dept_ids`**(전체)를 쓰는가 — `dept_id`(대표 1개) 아님
- [ ] `hint.deptFrom` 으로 **해제·삭제**까지 감지하는가
- [ ] 내 업무 일정의 제목을 캐시해 두는가 (삭제 후엔 조회 불가)
- [ ] `revision` 을 **먼저 갱신**하고 재조회하는가
- [ ] 티켓의 `revisions` 로 초기값을 채우는가
- [ ] 재접속 시 **재동기화**를 하는가
- [ ] 모르는 `type` 을 무시하는가 (예외를 던지지 않는가)
- [ ] 지수 백오프로 재접속하는가
- [ ] UI 갱신을 **UI 스레드로 마샬링**하는가
- [ ] 소켓이 끊겨도 **기존 수동 새로고침으로 동작**하는가
- [ ] 기기 토큰을 DPAPI 로 보관하는가

> 마지막 항목이 중요합니다. **실시간은 편의 계층입니다.**
> 서버가 멈추거나 인터넷이 끊겨도 프로그램은 평소대로 쓸 수 있어야 합니다.

| **revision** | 스코프별 변경 횟수. 정수, 단조 증가 |
| **module** | 구독 단위(기능 이름). 서버가 이걸 보고 Room 을 정함 |
| **Room** | 서버 내부의 전송 대상 그룹. **클라이언트는 알 필요도, 지정할 수도 없음** |
| **ticket** | 소켓 접속용 60초짜리 1회용 서명 토큰 |
| **device token** | 기기 고유 장기 자격증명. DPAPI 로 보관 |
| **echo** | 내가 만든 변경이 나에게 되돌아오는 것. `origin.clientId` 로 거름 |

## 부록 B. 서버 구성 요약 (참고용 · 수정 대상 아님)

```
future-class.kr (Apache + PHP)          node2.future-class.kr (Node.js)
